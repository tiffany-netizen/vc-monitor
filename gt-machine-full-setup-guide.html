Foundation / Prerequisite
Scenario 0: Supabase Database Setup
Every other scenario depends on this. Set up your central database first.
Do This First Supabase

Why this comes first

Right now your data lives in Gobii, RecruiterFlow, a Python HTML file, and your head. Nothing talks to each other because there's no shared database. Supabase becomes the single place everything writes to and reads from. Your Bolt UI already connects to it. Once these tables exist, every other scenario has somewhere to put its data.

Prerequisites

Supabase account with a project created
Your Supabase project URL (Settings > API > Project URL)
Your anon key and service_role key (Settings > API > Project API keys)

Steps

1

Open the Supabase SQL Editor

Supabase Dashboard
▶

Log into your Supabase project. In the left sidebar, click "SQL Editor". Click "New query" in the top left. You'll paste each CREATE TABLE statement here and hit "Run".

2

Create the "companies" table

Supabase SQL Editor
▶

Companies comes first because people reference companies via foreign key. Paste this SQL and click Run:

CREATE TABLE companies ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), name TEXT NOT NULL, website TEXT, jobs_url TEXT, tier TEXT CHECK (tier IN ('Tier 1','Tier 2','Tier 3','Machine','VC')), vc_investor TEXT, funding_stage TEXT, funding_amount TEXT, last_funding_date DATE, dna_fit BOOLEAN DEFAULT false, portfolio_of TEXT, headcount INTEGER, industry TEXT, status TEXT DEFAULT 'active', last_scraped TIMESTAMPTZ, rf_id TEXT, created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now() );
Tip: The rf_id column stores the RecruiterFlow company ID so you can match records between systems and avoid duplicates.
3

Create the "people" table

Supabase SQL Editor
▶
CREATE TABLE people ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), name TEXT NOT NULL, email TEXT, title TEXT, company_id UUID REFERENCES companies(id), company_name TEXT, tier TEXT CHECK (tier IN ('Tier 1','Tier 2','Tier 3','VC','OG')), source TEXT DEFAULT 'recruiterflow', enriched BOOLEAN DEFAULT false, email_found BOOLEAN DEFAULT false, status TEXT DEFAULT 'queued', linkedin_url TEXT, phone TEXT, last_job_change TIMESTAMPTZ, previous_title TEXT, previous_company TEXT, warm_intro_path TEXT, archive_reason TEXT, rf_id TEXT UNIQUE, apollo_id TEXT, created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now() );
Key fields: "status" drives what shows in your UI queue. Values: queued (new, needs review), active (being worked), enriched (Apollo data pulled), drafted (email ready), sent (email sent), archived (not actionable). "previous_title" and "previous_company" let you detect job changes in Scenario 9.

Create the "jobs" table

Supabase SQL Editor
▶
CREATE TABLE jobs ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), company_id UUID REFERENCES companies(id), company_name TEXT, title TEXT NOT NULL, url TEXT, source TEXT CHECK (source IN ('scrape','vc_portco','og_forum','manual')), dna_fit BOOLEAN DEFAULT false, first_seen TIMESTAMPTZ DEFAULT now(), last_seen TIMESTAMPTZ DEFAULT now(), status TEXT DEFAULT 'new', warm_contact_id UUID REFERENCES people(id), warm_contact_name TEXT, vc_source TEXT, vc_firm_id UUID REFERENCES vc_firms(id), notified BOOLEAN DEFAULT false, created_at TIMESTAMPTZ DEFAULT now() ); -- Index for fast lookups by company and status CREATE INDEX idx_jobs_company ON jobs(company_id); CREATE INDEX idx_jobs_status ON jobs(status); CREATE INDEX idx_jobs_source ON jobs(source);
Key fields: "source" tells you where the job came from (Gobii scrape, VC portfolio scraper, OG forum post, or manual entry). "warm_contact_id" links to a person you know at that company. "vc_source" stores which VC firm's portfolio the company belongs to.

Create the "drafts" table

Supabase SQL Editor
▶
CREATE TABLE drafts ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), person_id UUID REFERENCES people(id), company_id UUID REFERENCES companies(id), job_id UUID REFERENCES jobs(id), type TEXT CHECK (type IN ('outreach','follow_up','og_intro','job_change','funding')), subject TEXT, body TEXT, to_email TEXT, to_name TEXT, status TEXT DEFAULT 'draft', gmail_draft_id TEXT, sent_at TIMESTAMPTZ, skipped_at TIMESTAMPTZ, skip_reason TEXT, created_at TIMESTAMPTZ DEFAULT now() );
Status values: draft (AI generated, needs review), reviewed (you looked at it), sent (email went out), skipped (you decided not to send). The gmail_draft_id field stores the Gmail API draft ID so you can link back to it.

Supabase SQL Editor

CREATE TABLE activity_log ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), type TEXT NOT NULL, scenario TEXT, person_id UUID REFERENCES people(id), company_id UUID REFERENCES companies(id), job_id UUID REFERENCES jobs(id), details JSONB, created_at TIMESTAMPTZ DEFAULT now() ); CREATE INDEX idx_activity_type ON activity_log(type); CREATE INDEX idx_activity_created ON activity_log(created_at);

This table logs everything the system does. Types: enrichment, scrape, draft_created, email_sent, archived, job_change, funding_alert, slack_notified. Your weekly digest (Scenario 5) pulls from this table.

9

Create an "updated_at" auto-update function

Supabase SQL Editor
▶

This function automatically sets updated_at whenever a row in people or companies changes. Paste and run:

CREATE OR REPLACE FUNCTION update_updated_at() RETURNS TRIGGER AS $$ BEGIN NEW.updated_at = now(); RETURN NEW; END; $$ LANGUAGE plpgsql; CREATE TRIGGER people_updated_at BEFORE UPDATE ON people FOR EACH ROW EXECUTE FUNCTION update_updated_at(); CREATE TRIGGER companies_updated_at BEFORE UPDATE ON companies FOR EACH ROW EXECUTE FUNCTION update_updated_at();
10

Set up Row Level Security (RLS)

Supabase Dashboard
▶

RLS controls who can read/write your tables. For your setup, you want your Bolt UI (using the anon key) to have full access, and Make.com (using the service_role key) to bypass RLS entirely.

-- Enable RLS on all tables ALTER TABLE people ENABLE ROW LEVEL SECURITY; ALTER TABLE companies ENABLE ROW LEVEL SECURITY; ALTER TABLE jobs ENABLE ROW LEVEL SECURITY; ALTER TABLE drafts ENABLE ROW LEVEL SECURITY; ALTER TABLE vc_firms ENABLE ROW LEVEL SECURITY; ALTER TABLE activity_log ENABLE ROW LEVEL SECURITY; -- Allow anon key full access (your Bolt UI uses this) CREATE POLICY "Allow all for anon" ON people FOR ALL USING (true) WITH CHECK (true); CREATE POLICY "Allow all for anon" ON companies FOR ALL USING (true) WITH CHECK (true); CREATE POLICY "Allow all for anon" ON jobs FOR ALL USING (true) WITH CHECK (true); CREATE POLICY "Allow all for anon" ON drafts FOR ALL USING (true) WITH CHECK (true); CREATE POLICY "Allow all for anon" ON vc_firms FOR ALL USING (true) WITH CHECK (true); CREATE POLICY "Allow all for anon" ON activity_log FOR ALL USING (true) WITH CHECK (true);
Note: The service_role key bypasses RLS automatically. Use the service_role key in Make.com and your Python scraper. Use the anon key in your Bolt UI frontend. If you later add authentication to Bolt, you can tighten these policies.

Steps

1

Create a new Make.com Scenario called "S1 - RF Contact Ingest"

Make.com
▶
a. Log into Make.com. Click "Create a new scenario".
b. Name it "S1 - RF Contact Ingest".
c. Set the schedule: click the clock icon at the bottom. Set to run every 15 minutes (or every hour if you want fewer API calls).
2

Add the first module: HTTP "Make a request" to poll RecruiterFlow

Make.com > HTTP Module
▶

There are two approaches. Option A uses the Search endpoint to pull only tagged contacts (fewer API calls). Option B uses the List endpoint and filters in Make.com. Option A is better.

Option A: Use Contact Search (recommended)

a. Click the "+" to add a module. Search for "HTTP" and select "Make a request".
b. Method: POST
c. URL: https://api.recruiterflow.com/api/external/contact/search
d. Headers: RF-Api-Key = your RecruiterFlow API key, Content-Type = application/json
e. Body: Filter for the "Machine" tag (ID 2500). Any contact that should be synced gets the "Machine" tag in RecruiterFlow first, then this scenario picks it up:
{ "items_per_page": "50", "current_page": "1", "conjunction": "match-any", "filters": [ {"filter_type": "multi-select", "conjunction": "in", "key": "tags", "values": [2500]} ] } // "Machine" tag ID = 2500 // Use GET /api/external/tags/list to look up other tag IDs // The search endpoint handles filtering server-side // No Make.com filter needed after the Iterator

Option B: Use Contact List (simpler, but pulls all contacts)

a. Method: GET
b. URL: https://api.recruiterflow.com/api/external/contact/list?items_per_page=50¤t_page=1&include_count=true
c. Headers: RF-Api-Key = your RecruiterFlow API key
d. This returns all contacts (paginated). You'd then filter by tags in the next step.
Important: The base URL is api.recruiterflow.com (not recruiterflow.com). The response comes back as {"data": [...], "total_items": N}. Your contacts are in the "data" array. Pagination: increase current_page to get the next batch. Run a loop in Make.com if you have more than 50 tagged contacts.
3

Add an Iterator module to loop through returned contacts

Make.com > Flow Control > Iterator
▶
a. Add a "Flow Control > Iterator" module after the HTTP request.
b. Set the Array field to {{body.data}} from the HTTP module (the "data" array in the response).
c. This processes each contact one at a time through the remaining modules.
4

No Make.com filter needed (API handles it)

Make.com > Filter (skip this step)
▶

Since the POST search endpoint filters for the "Machine" tag server-side, you don't need a Make.com filter between the Iterator and Supabase. Every contact returned already has the Machine tag.

a. The upsert with on_conflict=rf_id handles deduplication automatically. If a contact already exists, it updates instead of creating a duplicate.
b. If you want to only sync newly added contacts (not re-upsert everyone each run), add a date filter: {"filter_type": "date", "key": "added_on", "conjunction": "gte", "values": ["2026-04-04"]} to the search body. Update the date as needed, or use Make.com's built-in "last run" timestamp.
5

Add a Supabase HTTP module: Upsert contact into "people" table

Make.com > HTTP Module > Supabase REST API
▶

Make.com doesn't have a native Supabase module, so use an HTTP request to hit Supabase's REST API.

a. Add another HTTP "Make a request" module.
b. Method: POST
c. URL: https://jhreeyesdtnmanolmjqu.supabase.co/rest/v1/people?on_conflict=rf_id
d. Headers (add all four):
apikey = your service_role key
Authorization = Bearer your_service_role_key
Content-Type = application/json
Prefer = resolution=merge-duplicates, return=representation
e. Body (JSON):
{ "rf_id": "{{iterator.id}}", "name": "{{iterator.first_name}} {{iterator.last_name}}", "email": "{{iterator.email}}", "title": "{{iterator.title}}", "company_name": "{{iterator.company_name}}", "tier": "{{iterator.tag_that_matched}}", "linkedin_url": "{{iterator.linkedin_url}}", "phone": "{{iterator.phone}}", "source": "recruiterflow", "status": "queued" }
f. The "Prefer: resolution=merge-duplicates" header tells Supabase to update the existing row if rf_id already exists (upsert behavior). For this to work, you need a unique constraint on rf_id. Run this SQL in Supabase if you haven't already:
ALTER TABLE people ADD CONSTRAINT people_rf_id_unique UNIQUE (rf_id);
Field mapping: The field names inside {{iterator.xxx}} depend on what RecruiterFlow returns. Run the scenario once, look at the HTTP output, and map the actual field names RF uses to your Supabase column names.
6

Test the full scenario end-to-end

Make.com + RecruiterFlow + Supabase
▶
a. In RecruiterFlow, add or update a test contact and tag them "Tier 1".
b. In Make.com, click "Run once".
c. Watch each module execute. Green = success, red = error.
d. Check Supabase: go to Table Editor > people. You should see the new contact with status "queued".
e. Check Bolt UI: refresh and verify the contact appears in the queue.
f. If everything works, turn on the scenario schedule (toggle at the bottom left of the scenario editor).
